# CA9 Case Production & Supply System v1

## Responsibility and scope
This is a simulation control plane, not an autonomous model or a model API. GitHub Actions runs deterministic Python validation and stock reconciliation. ChatGPT authors real original fictional records and does actual legal research in active turns. A queue entry is a request for work, not a completed case. Do not claim it is produced before seal. No real elapsed time advances the judicial simulation. No external API or paid service is added.

- Creator: `supply/STATE.json` and `supply/requests/` / `supply/receipts/` (append-only requests and receipts). Never reveal future case titles, facts, theories, drafts or internal world records to the judge; public repository provides no technical confidentiality.
- Clerk: official `CURRENT.json` checkpoint, verified releases, per-case intake review and calendar slots, actual replayed events.
- Judge: assigned panel cases and notices in ChatGPT and the site. The Supply tab shows aggregate counts only, never an unassigned original. No external push notification is configured.

## Stock policy (simulation defaults, not actual caseload statistics)
Target 3 available or in-production cases; low-watermark 1; max 3 open jobs, intake/assignment batch max 2 per clerk turn. Ready = sealed and not admitted, exact campaign cutoff and no future filing. Registered-unassigned cases count toward available supply. Assigned and closed cases do not. Rework counts toward pipeline so failure does not generate unlimited jobs. Incompatible cutoff or future case records are blocked, not admitted. Before appointment, the provisional cutoff is 2026-11-27; the first release is a prepared stock item, not a live case. New work uses the actual configured cutoff after setup; old jobs are retained and blocked rather than silently rewritten. Track weights 40/25/25/10 for civil summary judgment/civil trial/criminal trial/criminal suppression; stable seeded draw, rotating districts. These weights are adjustable game design defaults. Unimplemented special tracks never enter queue.

## State machine
```
queued -> working -> world -> procedure -> record -> excerpts -> briefs -> reviewed
                     failed stage -> rework -> retry -> same failed stage
reviewed -> full revalidation and immutable release.json -> sealed
sealed -> official intake -> unassigned -> reviewed calendar draw -> assigned -> closed
```
Append unique lexically increasing request IDs; examples in templates/supply-request.json. Actions: request (optional track/district), start, progress (note), advance (next exact stage), retry, cancel (reason), seal (stage review). Each non-request specifies job_id and expected_status. Stage advancement actually runs the production compiler, including prior stages. Failure writes a reason receipt, leaves stage unchanged; failed seal returns to review. Retry increments attempt. Sealed jobs cannot be modified through the queue. A verified legacy release imports once. Future production uses queue jobs and supply seal; pre-existing standalone factory seal remains supported, but untracked releases are not stock. A valid seal is the compiler's real release with hashes; review gate cannot be bypassed by a queue note. Requests are not executable scripts.

Reconciliation triggers on supply request/policy changes, existing official save publication and factory seal. Same concurrency group as save and seal. It imports valid releases, records receipts, recomputes stock against official state, creates missing queued jobs up to capacity, writes STATE/PUBLIC with checkpoint and revision, publishes via fast-forward. Bot push does not need to trigger another workflow. Re-run sync safely; do not edit prior requests/receipts. No automatic creation of hundreds of pages. If blocked on legal research or tool/time limits, retain rework or working state and continue a later active producer turn.

## Clerk workflow per actual play turn
1. Read official checkpoint and supply/PUBLIC at same HEAD; if snapshot revision differs, reconcile; never invent an accepted receipt. If setup_required, no admission or assignment.
2. When calendar workload warrants intake, read creator supply metadata separately. Use oldest eligible sealed case first, with jurisdiction and conflict review of actual case and roster. A documented defer_reason can skip an older case, never select a favored result. Submit ca9.supply_intake in ordinary request JSON, with case-specific reviews (see template). Processor selects oldest eligible and expands to normal ca9.factory_admit and document.register. The initial cutoff/date gates, release hash and original documents are verified. It is not a new appeal before accepted receipt.
3. The clerk prepares actual simulated sitting slots in appropriate location/month, based on roster availability, conflicts and GO priority review, including total_weight for each slot. Submit ca9.clerk_calendar with reviews for oldest unassigned cases, possibly after intake in the same batch if already configured. This processor selects FIFO subject to reviewed deferrals, subtracts existing assigned weights for the same location/month/slot, uses deterministic draw seed from event ID/case/month and existing ca9.assign checks. Does not guarantee player's assignment; does not auto invent calendar or conflict clearance. Existing direct ca9.assign remains a legacy lower-level event; use clerk route for supply. Never reroll to give player a case. No available reviewed slot -> no assignment.
4. On accepted receipt and reread CURRENT, compare actual panel membership/assignment history to prior official checkpoint. If player newly assigned, issue in-character notice (English original plus optional Korean explanation): "OFFICE OF THE CLERK — Notice of Case Assignment. A case has been assigned to your panel. The appellate briefs and excerpts of record are available in your chambers docket." Include actual case ID, caption, panel and record link. No notice for cases assigned to others or mere stock. Browser displays current panel assignment notices derived from actual panel history; no unread flag or push notification.
5. Replenishment request automatically created by reconciliation when needed; during active ChatGPT turns, work the oldest queued/working/rework job as a separate creator role without disclosing facts. Use CASE_FACTORY.md and LEGAL_RESEARCH.md, author genuine full records and run stages. If production is not complete, tell judge only aggregate shortage, not a fabricated new case. A regular play action can trigger clerk administration without player asking for a particular case; time advancement still needs user authorization.

## Limitations
No unattended AI worker; no automatic review of material legal uncertainty, no actual calendar schedule persisted independently of assignments, no automatic appointments. Conflict and calendar reviews require actual reviewed inputs; current court profile readiness and roster installation still gate live play. Stock state is a derived operational ledger plus append-only receipts, not a second judicial state. Same-model role separation and public GitHub are not secure barriers. Physical PDF export remains separate.
