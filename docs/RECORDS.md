# 기록과 사건 제작

## 원문 원칙

실제 플레이 사건은 사전 제작된 초기 기록이 있어야 한다. 목록·요약만 만들어 complete로 표시하지 않는다. 준비 중인 사건은 planning/에 두고 배당하지 않는다. 사건마다 initial_document_ids 목록의 원문이 모두 존재해야 저장 검증을 통과한다.

제출서면, 증거물, 녹취록, 명령, 의견서, 직원 보고는 별도 document ID와 immutable 경로를 갖는다. 실제 분량에 근접한 기록은 제작 작업량이 크다. 반복·과도한 줄바꿈·페이지 라벨만 늘려 분량을 부풀리지 않는다. examples는 작은 기능 검증 자료이며 실제 사건 분량의 표본이 아니다.

문서 첫머리에 `<!-- PAGE 1 -->`를 두고 실제 내용 단위에 따라 연속 PAGE 표시를 넣는다. 이는 고정된 **논리 쪽수**이며 렌더링된 PDF의 쪽수와 같다고 주장하지 않는다. PDF가 필요하면 별도 생성·검수 후 논리 쪽수와의 대응을 고정한다. 문서 인용은 document_id + 논리 page로 한다. 프로그램은 쪽의 존재를 검사할 뿐 그 쪽이 논증을 지지하는지 판단하지 않는다.

원문은 영어를 기본으로 하고 진행·설명은 한국어를 기본으로 한다. 사용자가 번역을 요청하면 원문과 구분해 제공한다. 번역·요약을 원문으로 교체하지 않는다.

## 접근 층

| access/status | 의미 |
|---|---|
| judge/filed | 재판부에 제출되어 판사가 볼 수 있는 기록 |
| judge/internal | 합법적으로 재판부가 볼 수 있는 메모·초안 등 |
| world_only/unfiled | 세계에는 있으나 재판부에 제출되지 않은 자료 |
| npc_private/internal | 인물의 사적 정보·작업 자료 |

판사의 접근 권한이 있더라도 공개 문서라는 의미는 아니다. 봉인·보호명령·변호사 비밀 등은 별도 필드와 법원별 검토를 추가한다. 한 private 저장소에 저장하므로 사용자·모델에 대한 기술적 비밀 장벽은 없다. 운영상 누출 방지이며 독립 비밀 GM 서버가 아니다.

## 제작 순서

1. planning에 객관 사실·시간표·인물 인식·쟁점·문서 관계를 설계한다.
2. 사건 관할·절차와 법률 자료를 조사하고 source ID로 기록한다.
3. 자연스럽게 발생하는 문서 원문을 여러 배치에 걸쳐 작성한다.
4. 인물·날짜·금액·시간대·증거 관계를 대조한다. 실제 원문 쪽을 인용하게 한다.
5. 초기 기록 inventory와 문서 해시를 고정하고 준비 완료를 확인한다.
6. 배당과 document.register 이벤트를 같은 저장 요청에 넣는다.
7. 후속 제출은 실제 제출된 game_time에 새 문서로 추가한다. 기존 증거의 내용을 질문에 맞춰 바꾸지 않는다.

법적 결론은 단일 정답으로 미리 강제하지 않는다. 사실은 고정하고 논증·기록·절차에 따른 복수 결론을 허용한다. 평가/후속 효과는 해당 법원과 기록에 근거한다.

## 정정

원문 파일을 덮어쓰지 않는다. 새 ID·경로·버전으로 등록하고 supersedes에 기존 ID를 적는다. 정정 제출의 원인과 시점을 기록한다. 과거 원문과 인용을 보존한다. 오류 정정으로도 이미 내려진 판결이 조용히 소급 변경되지는 않는다.
